# 运行资源与性能

## 已处理的开销

- GDI 兼容抓屏按原始输入尺寸计算帧队列，目标约 64 MiB，最多 8 帧、最少 1 帧。1920×1080 使用 8 帧，2560×1440 使用 4 帧，3840×2160 使用 2 帧；单帧超过预算时仍保留一帧。原先 512 帧的队列在 4K 编码积压时理论上可占约 15.8 GiB。该限制仅约束输入队列，不是 FFmpeg 或软件的总内存上限；编码器、GPU 表面、滤镜和音频还需要内存。
- 音量条只在声音页可见、启用声音且需要更新时运行 100 ms 定时器。隐藏、最小化、离开声音页、暂停或处理文件时停止电平轮询；空闲预览设备随页面隐藏立即释放。实际录音由独立音频会话负责。
- 浮窗复用当前字体，一次生成速度、开始时间和剩余时间文案；主窗口帧数按原有 500 ms 周期和状态切换刷新，停止后立即显示最终计数。相同电平和滚动条参数不重复要求重绘。
- 连续录像对已关闭的分段只累计一次字节数，平时检查当前分段及下一个文件；停止、恢复和合成时仍完整校验连续素材。 磁盘保护的素材总大小通过目录项批量读取属性，避免逐个文件重新查询。
- FFmpeg 进度解析提前跳过无关字段，避免反复生成子字符串。主窗口退出或切换语言时释放自己创建的图标及 logo 位图。

这些修改不更换编码器，不改变所选分辨率、帧率或画质。编码跟不上时，有限缓冲会更早产生反压，不保证消除采集掉帧。

## 检查方法

```powershell
powershell -ExecutionPolicy Bypass -File tests/Run-Regression.ps1 -Resources
```

专项会报告空闲全屏模式、空闲区域模式下 4 秒窗口内的 CPU 时间、托管分配、进程专用内存、GDI 对象和电平定时器状态，并执行真实滚动分段、暂停继续、RGB 帧哈希及字体复用检查。 帧哈希解码使用 passthrough，避免校验工具按固定帧率补帧或跳过重复时间戳帧。`-ResourceProfile` 只运行空闲测量。

测量对象是测试宿主，包含测试代码及已加载组件，不能直接当作发行 EXE 的精确占用。冷启动、JIT、杀毒扫描、系统省电策略与其他程序都会影响短时读数；应固定硬件、画面和参数，多次采样后比较。不要把不足一个计时粒度的 CPU 差异当作提升百分比。

主程序与录制中的 FFmpeg 是独立进程。任务管理器中应同时观察两者的 CPU、专用内存、GPU Video Encode 和磁盘写入；只看主程序会漏掉主要编码开销。无损高分辨率录制仍可能大量占用 CPU、GPU、磁盘和保存空间。

## 仍需实机验证

不同编码器、驱动、多屏、数小时录制和声卡热插拔仍按 [硬件验证范围](HARDWARE-VALIDATION.md) 验证。本机的短时资源和帧一致性检查不能替代这些场景。
